# BloodNet — شبکه هماهنگی زنجیره تأمین خون

نسخه تمرینی محصول BloodNet بر اساس صورت‌مسئله و Participant Kit مسابقه. تمام داده‌ها، قواعد و شناسه‌ها ساختگی‌اند و این نرم‌افزار **برای تصمیم‌گیری پزشکی یا استفاده در انتقال خون واقعی نیست**.

## معماری تحویل‌شده

- **هسته مسابقه:** Python 3.10+ در `service/bloodnet_api.py`، روی `http://127.0.0.1:8000` و منطبق با مسیرهای اصلی `openapi.yaml`.
- **رابط وب متصل به API:** در `web/`؛ شامل گردش‌کار بیمارستان، فهرست و جزئیات درخواست، موجودی مرکز و پرتال آزمایشی اهداکننده.
- **سرویس‌های شبیه‌ساز کیت:** Gateway روی 9100، Travel روی 9200 و Inventory روی 9300؛ کد آن‌ها در `harness/` است.
- **داده‌ها و قواعد:** از `participant_kit/` خوانده می‌شوند؛ ماتریس سازگاری از `compat.yaml` و شرایط اهدا از `rules.yaml` بارگذاری می‌شوند.
- **نمونه PHP/MySQL:** فایل‌های PHP و `database/schema.sql` از نسخه اولیه حفظ شده‌اند. آن‌ها یک نمونه آموزشی مستقل‌اند و منبع حقیقت API مسابقه نیستند. برای دمو و ارزیابی مسابقه از `web/index.html` و API پایتون استفاده کنید.

## راه‌اندازی سریع در ویندوز

### ۱) نصب پیش‌نیازها

- Python 3.10 یا جدیدتر
- نصب وابستگی‌ها:

```bash
pip install -r requirements.txt
```

### ۲) اجرای نسخه وب محلی

برای نصب وابستگی‌ها و اجرای همه اجزا با یک فرمان، `run-local.bat` را اجرا کنید؛ یا اگر وابستگی‌ها نصب‌اند `start-local-demo.bat` را اجرا کنید. پنج پنجره باز می‌شود:

- Gateway: `http://127.0.0.1:9100`
- Travel: `http://127.0.0.1:9200`
- Inventory: `http://127.0.0.1:9300`
- BloodNet API: `http://127.0.0.1:8000`

رابط وب به‌صورت خودکار روی `http://127.0.0.1:8080` سرو می‌شود. همچنین می‌توانید پوشه پروژه را با XAMPP سرو کنید و مسیر `/BloodNet-Mini/web/` را باز کنید. API هدرهای CORS را برای دموی محلی فعال کرده است.

### ۳) اجرای آزمون رسمی قرارداد

در حالی که API روی پورت 8000 اجراست:

```bash
python -m harness.contract_tests --team http://127.0.0.1:8000
```

یا `run-contract-tests.bat` را اجرا کنید. این تست سیاه‌جعبه قرارداد API کیت است.

### ۴) اجرای سناریوی تمرینی کامل

برای اجرای Runner، فقط API را روشن کنید (با `start-api.bat` یا `python service/bloodnet_api.py`). سپس در ترمینال دیگری اجرا کنید:

```bash
python -m harness.runner --team http://127.0.0.1:8000 --scenario P-normal --seed 1000
```

Runner خودش Gateway، Travel و Inventory را بالا می‌آورد؛ بنابراین هم‌زمان `start-local-demo.bat` را اجرا نکنید، چون پورت‌های شبیه‌ساز اشغال می‌شوند.

سناریوهای عمومی:

| سناریو | کاربرد |
|---|---|
| `P-normal` | جریان عادی درخواست، موجودی، دعوت و callback |
| `P-amend` | تغییر فوریت و لغو درخواست |
| `P-abuse` | تقاضای غیرعادی و بیمارستان ثبت‌نشده |

برای تست سریع‌تر می‌توانید از `--max-requests 8 --speed 480` استفاده کنید. نتیجه در `run_out/result.json` ذخیره می‌شود. برای هر اجرای مستقل، API را restart کنید؛ ساعت شبیه‌سازی و state سرویس در حافظه نگهداری می‌شوند.

## توکن‌های محیط تمرین

این توکن‌ها ثابت و مخصوص کیت تمرین محلی هستند؛ هیچ کلید یا سرویس پولی لازم نیست. آن‌ها را روی اینترنت عمومی منتشر نکنید و پورت 8000 را عمومی نکنید. برای محیط غیرمحلی، توکن‌ها و `CORS_ORIGIN` را در `.env` محدود و عوض کنید:

| نقش | توکن |
|---|---|
| Hospital API | `hospital-token` |
| Coordinator approval | `coordinator-token` |
| Donor demo portal | `donor-demo-token` |

برای تغییر تنظیمات، `.env.example` را به `.env` کپی و مقادیر را اصلاح کنید. فایل `.env` نباید حاوی اطلاعات واقعی یا محرمانه باشد.

## قابلیت‌های پیاده‌سازی‌شده

- قراردادهای `POST /requests`، `GET /requests/{id}`، لغو، اصلاح فوریت و تأیید درخواست در `openapi.yaml`.
- اعتبارسنجی نوع و مقدار ورودی‌ها، محدودیت ۲۰ واحد، رد فیلدهای اضافی، احراز هویت بیمارستان و هماهنگ‌کننده؛ rate limit ایجاد درخواست با پاسخ `429` و `Retry-After`.
- `Idempotency-Key` با مقایسه hash بدنه؛ درخواست تکراری با بدنه یکسان پاسخ تکراری می‌گیرد و بدنه متفاوت `422` می‌گیرد.
- خواندن ساعت از `GET /clock` سرویس Gateway؛ تصمیم‌های SLA، موج دعوت و eligibility با simulation time انجام می‌شوند.
- خواندن موجودی جاری از Inventory API؛ سازگاری از `compat.yaml`؛ انتخاب بر اساس FEFO؛ شناسه dispatch پایدار برای retry؛ کنترل رقابت با قفل در سطح درخواست و اتکا به dispatch اتمیک سرویس Inventory.
- اتصال به Gateway برای پیام‌های `request_wave`، `confirmed`، `not_needed` و `cancelled`؛ retry محدود برای خطاهای `429` و `503` و رعایت `Retry-After`.
- انتخاب اهداکننده بر اساس سازگاری، سن و وزن قواعد ساختگی، سوابق اهدا، تعلیق `defer_until`، ساعت سکوت، محدودیت اعلان ۹۰روزه، فاصله و سابقه پاسخ تاریخی؛ فاصله موج‌ها برای بحرانی/فوری/برنامه‌ریزی‌شده به‌ترتیب ۱۵/۳۰/۶۰ دقیقه شبیه‌سازی است.
- جلوگیری از تعهد هم‌زمان یک اهداکننده به چند درخواست و کنترل تعداد دعوت‌ها بر اساس کسری باقی‌مانده.
- پردازش callbackهای Gateway، deduplication با `event_id`، کنترل رویدادهای خارج از ترتیب با `sim_time`، شمارش تأمین فقط پس از `donated`.
- توقف دعوت‌های غیرضروری پس از تأمین، لغو یا انقضا؛ صف retry برای اعلان‌های پذیرفته‌نشده.
- سیاست بازبینی برای درخواست‌های مشکوک: درخواست بحرانی ۸ واحدی، سومین درخواست با fingerprint کاملاً یکسان در ۶۰ دقیقه شبیه‌سازی یا ششمین درخواست یک بیمارستان در همین بازه به `pending_review` می‌رود و پیش از تأیید هماهنگ‌کننده هیچ موجودی یا دعوتی مصرف نمی‌کند.
- ثبت رویدادهای قابل مشاهده در جزئیات درخواست و رابط وب سه‌نقشی.

صورت‌مسئله و راهنمای داوری اصلی نیز برای مراجعه در `docs/reference/` قرار دارند. جزئیات فنی و مرزهای هر قابلیت در `DECLARED.md` و `docs/ARCHITECTURE.md` آمده است.

## مسیر دموی پیشنهادی (۵ دقیقه)

1. `start-local-demo.bat` را اجرا و `web/index.html` را باز کنید.
2. از پنل بیمارستان یک درخواست با گروه `O+`، فرآورده `red_cells` و فوریت `critical` ثبت کنید.
3. شناسه درخواست را در فهرست باز کنید و شمارنده‌های `confirmed`، `en_route`، `arrived` و `fulfilled` را ببینید.
4. پنل موجودی را باز کنید؛ موجودی از Inventory API خوانده می‌شود، نه از CSV اولیه.
5. در صورت وجود دعوت، در پرتال اهداکننده شناسه آزمایشی را وارد کنید و مسیر پذیرش/پیشرفت را نمایش دهید. این پرتال فقط برای دمو است؛ Runner واقعی callbackها را از Gateway می‌فرستد.
6. در `P-abuse` نشان دهید درخواست‌های پرریسک در `pending_review` می‌مانند و درخواست H98 رد می‌شود.

## تست‌ها و شواهد

```bash
python -m harness.contract_tests --team http://127.0.0.1:8000
python tests/extended_contract.py http://127.0.0.1:8000
```

سناریوهای تمرینی و گزارش‌های تولیدشده در `run_out_*` نمونه‌اند و امتیازشان به seed، سرعت شبیه‌سازی و تعداد درخواست‌ها وابسته است؛ آن‌ها را معادل نتیجه ارزیابی نهایی ندانید.

## محدودیت‌های شناخته‌شده

- state هسته مسابقه (درخواست‌ها، idempotency و event dedupe) در حافظه نگهداری می‌شود و با restart پاک می‌شود. این مطابق workflow تمرینی کیت است که توصیه می‌کند بین اجراها سرویس restart شود؛ برای سامانه تولیدی باید storage پایدار و transactional اضافه شود.
- API مسابقه از PHP/MySQL قدیمی استفاده نمی‌کند؛ فایل‌های PHP/MySQL حفظ شده‌اند اما دیتابیس آن‌ها با state سرویس پایتون همگام نیست. پنل اصلی مسابقه `web/` است.
- پرتال اهداکننده مسیر کمکی دمو است؛ در ارزیابی رسمی، رفتار اهداکننده و callbackها را Gateway شبیه‌سازی می‌کند.
- این نسخه قابلیت AI امتیازآور ادعا نمی‌کند. بخش هوشمند مسابقه اختیاری است و برای آن باید یک ماژول محلی قابل ارزیابی و مستند اضافه شود.
- این نرم‌افزار، قواعد سازگاری و داده‌ها فقط برای مسابقه و شبیه‌سازی‌اند؛ برای مراقبت، تشخیص، غربالگری یا انتقال خون واقعی مناسب نیستند.

## بررسی درخواست‌های پرریسک توسط هماهنگ‌کننده

در رابط وب، از منوی «بررسی و تأیید درخواست‌ها» صف درخواست‌های `pending_review` را باز کنید. توکن دموی هماهنگ‌کننده در محیط محلی `coordinator-token` است. هماهنگ‌کننده پس از مشاهده جزئیات و تاریخچه می‌تواند درخواست را تأیید کند یا با ثبت دلیل آن را رد کند. تأیید، وضعیت را به `open` تغییر داده و فرآیند تأمین را فعال می‌کند؛ رد، وضعیت را `cancelled` می‌کند و رویداد `review_rejected` همراه با دلیل در تاریخچه ذخیره می‌شود. تصمیم‌گیری مجدد روی درخواست تعیین‌تکلیف‌شده با پاسخ 409 مسدود است.

برای آزمون گردش کار بررسی هماهنگ‌کننده، پس از اجرای API دستور زیر را اجرا کنید:

```bash
python tests/coordinator_review.py http://127.0.0.1:8000
```

در رد درخواست، یادداشت تصمیم الزامی است. توکن هماهنگ‌کننده فقط برای دموی محلی است و در استقرار واقعی باید با احراز هویت و نقش‌های امن جایگزین شود.
